# 架构与设计边界

## 设计目标

本 Skill 优化的是复杂项目的决策流和资源分配，而不是单次回答的语言风格。它试图减少四类成本：

1. 中文需求在长链路中被遗漏、弱化或错误翻译；
2. 尚未明确范围就开始实现造成的返工；
3. 无边界并行、重复读取和重复实现造成的 token 浪费；
4. 实现者自行宣布完成而缺少独立证据。

## 关键组件

| 组件 | 责任 | 默认语言 |
| --- | --- | --- |
| 协调 agent | 权限边界、计划、资源预算、集成和用户沟通 | 内部英文，用户界面中文 |
| Intake agent | 将实质性输入编译成紧凑英文需求规格 | 英文 |
| 执行 agent | 仅处理有边界的重型或独立工作流 | 英文 |
| 验收 agent | 按原需求与确认标准做全新只读审查 | 英文输入，结论由协调 agent 忠实转为中文 |

原始用户消息始终是需求权威来源。英文规格是便于内部执行的中间表示，不是替代合同。

## Intake 策略

`intake_policy: economy` 是默认策略：只有会改变项目目标、交付物、约束、验收或实现方向的中文/混合语言消息才创建一次性 intake agent。批准、停止、继续、选项选择和纯状态查询在本地转成英文控制指令。

`intake_policy: strict` 为需要完整前置审计的环境保留：所有项目消息都经过全新 intake agent。它更昂贵，但边界更统一。

执行速度是独立维度。`execution_mode: economy` 默认串行并减少上下文转移；`execution_mode: fast` 只在用户优先要求墙钟速度、且工作流确实独立时启用有边界的并行。

## 计划与授权

计划批准只允许进入已确认的实现范围。以下动作不会被隐式授权：

- 发布、部署或生产环境修改；
- 发送邮件、消息或邀请；
- 使用付费服务或扩大资源配额；
- 安装持久化第三方 Skill、插件或 hooks；
- 运行未明确描述的 smoke test；
- 使用真实敏感数据进行验证。

测试可在计划阶段预授权，但必须已经确定真实命令/步骤、目标环境、数据、成本、风险和成功条件，而且不得包含不可逆或外部副作用。任一要素发生实质变化，原授权失效。

## 资源模型

- `light`：一个交付物或高度耦合的工作；协调 agent 串行完成。
- `standard`：多阶段但单一上下文仍可管理；可以加载专业 Skill，但不增加执行 agent。
- `heavy`：大规模材料、多专业领域、长构建，或 `execution_mode: fast` 下存在真正独立的工作流；才增加少量、有停止条件的执行 agent。

Intake 与最终验收 agent 是工作流固定角色，不计入“执行 agent”。缺少子 agent 能力时必须向用户说明降级；协调 agent 的第二次自检不能冒充独立验收。

## 状态与恢复

有稳定代码仓库时，状态保存在 `.codex/zh-complex-project-state.md`。非代码项目可以使用宿主提供、且经用户批准的持久文件位置。若没有持久后端，只能生成中文 checkpoint，并明确说明新线程无法可靠恢复。

恢复时不能只相信状态摘要；应核对当前产物、版本和未决决策。状态完成、暂停、停用、过期或相互冲突时不得静默重新激活。新线程中的状态文件不能自行触发 Skill；用户必须先显式调用。

## 第三方能力

Grill Me、Ponytail 和 Nature Skills 都是可选能力，不是运行依赖。本 Skill 只记录来源和路由原则，不捆绑其代码。安装需要当前用户明确授权，并继续受宿主审批机制约束。

## 平台限制

- Agent Skill 在协调 agent 收到消息后才可能运行，因此不能提供真正的网络或宿主级 prompt 拦截。
- Plan、子 agent、持久存储和 Skill 安装能力由宿主决定。
- 跨新会话的自动激活不受普通 Skill 完全控制；需要显式调用、可靠状态恢复，或另行实现宿主插件/hook。
- 本仓库不声明任何工具为预授权工具；实际权限始终由用户和宿主决定。

## 为什么使用渐进披露

`SKILL.md` 只保留每次激活都必须知道的门禁。完整资源预算和状态契约位于 `references/workflow.md`，第三方规则位于 `references/external-skills.md`，维护测试位于 `references/test-cases.md`。这样普通运行不会加载所有维护资料。
